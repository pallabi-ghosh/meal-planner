# Meal Planner

A self-hosted family meal planner. Plan the week, get a categorised grocery list, and log what you actually ate, so the plan fits the household better over time.

It runs on your own computer, uses a **local LLM (Ollama)** for planning, stores everything in plain JSON files, and has no accounts, no database, and no cloud dependency. Email delivery via [Resend](https://resend.com) is optional.

> **Status: work in progress.** v1 (single household, plan → grocery → log → email) is complete and in daily use. v2 (profiles, calories, taste files, date-range groceries) is being built on top of it. See [Roadmap](#roadmap).

## Features

**Available now**

- **Week plan, generated by a local model.** An agent loop gets your household's preferences and pantry through tool calls, then submits a structured week. The result is validated (valid meal slots and people, hard rules such as "no rice at lunch") and retried up to three times.
- **Editable plan.** Add or remove dishes per meal slot (breakfast, lunch, snack, dinner); no regeneration needed.
- **Editable, categorised grocery list.** Free-text items ("box of eggs", "2 packets of milk"), auto-grouped into Produce, Dairy, Meat & Fish, Bakery, Pantry, Frozen, Beverages, Household. Tick off what you already have. Adding something that is already on the list asks whether to update the line or add a new one.
- **Per-person logging.** Mark each planned meal as eaten or substituted, per profile. Substitutions nudge the accept/reject counts of the matching preference, and you can add your own preferences directly.
- **Email.** Send the meal plan and the categorised grocery list through Resend.
- **Phone-friendly.** Three tabs (Week, Log, Grocery) with a bottom tab bar on small screens.

**Foundation for v2 (in the codebase, UI in progress)**

- **Profiles and food rules** (`/profiles`): adults with body details for calorie targets, a child with food rules (no added sugar or salt, texture, allergens). Each profile saves on its own.
- **Usual meals** per person, kept in a Markdown taste file (`data/taste/<profile>.md`) you can also edit by hand. The child's dinner is a short pool to pick from. An optional Ollama call suggests ingredients, filtered by the child's food rules.
- Structured recipes (ingredient, quantity, unit), pantry and bought ledger, and taste-file proposal types (data model only so far).
- Atomic JSON writes with a per-file queue, so two devices can edit at once without corrupting data.

## Screens

| Tab | What it does |
| --- | --- |
| **Week** | Family-level planning. Generate a week, edit dishes by meal slot. Pick a person to see their read-only view. |
| **Log** | Per-profile feedback. Yes / something else for each meal, plus "push your own suggestion". |
| **Grocery** | The shopping list: add, tick off, remove, send by email. |

Planning and groceries are family-level; logging is per person.

## Tech stack

- [Next.js 16](https://nextjs.org) (App Router, Turbopack), React 19, TypeScript (strict)
- [Ollama](https://ollama.com) for the LLM (default model: `llama3.2`), via its tool-calling chat API
- [Resend](https://resend.com) for email (optional)
- JSON files on disk for storage

## Quick start

**Prerequisites**

- Node.js 20.9 or newer
- [Ollama](https://ollama.com/download) installed and running
- (Optional) a [Resend](https://resend.com) API key if you want email

```bash
git clone https://github.com/pallabi-ghosh/meal-planner.git
cd meal-planner
npm install

cp .env.local.example .env.local   # then edit it (see below)

ollama pull llama3.2
ollama serve                       # skip if Ollama is already running

npm run dev
```

Open <http://localhost:3000>. Click **Generate week** on the Week tab.

### Configuration

Set these in `.env.local` (never commit this file; it is gitignored):

| Variable | Default | Purpose |
| --- | --- | --- |
| `OLLAMA_BASE_URL` | `http://127.0.0.1:11434` | Where Ollama is listening |
| `OLLAMA_MODEL` | `llama3.2` | Model used for planning. It must support tool calling |
| `RESEND_API_KEY` | none | Enables email. Without it, email is skipped |
| `TO_EMAILS` | none | Comma-separated recipients for the plan and grocery email |

Email is sent from Resend's shared test address (`onboarding@resend.dev`). That is meant for testing; to email other people, verify your own domain in Resend and change the `from` address in [`lib/email.ts`](lib/email.ts).

### Make it yours

Your household's starting preferences live in [`data/seed-preferences.json`](data/seed-preferences.json): hard rules, ratios, frictions, and pantry carry-over. Edit this file to describe your own household before generating your first week. The bundled content is an example family's preferences.

## Using it from your phone

The app is built for a phone at the shop, not just a laptop.

- **Same Wi-Fi:** open `http://<your-computer's-LAN-IP>:3000` on the phone.
- **From anywhere:** put the computer and phone on a private network such as [Tailscale](https://tailscale.com) and use the computer's Tailscale address.

In development, Next.js blocks requests from origins it doesn't recognise. Add your computer's address to `allowedDevOrigins` in [`next.config.js`](next.config.js), then restart `npm run dev`.

## How it works

```
Browser (Week / Log / Grocery tabs)
        │
        ▼
Next.js API routes  ──►  lib/agent.ts    tool-calling loop against Ollama
 (app/api/*)        ──►  lib/grocery.ts  ingredient merge + category rules (plain code, not the LLM)
                    ──►  lib/email.ts    HTML email via Resend
                    ──►  lib/store.ts    atomic JSON reads/writes
                              │
                              ▼
                        data/*.json
```

**Generating a week**

1. The agent is told the household's constraints and given three tools: `get_preferences`, `get_pantry`, and `submit_week_plan`.
2. It calls the lookup tools for context, then must submit the plan through `submit_week_plan`, whose parameter schema constrains meal slots and people to fixed values.
3. If the model answers in plain text instead of calling a tool, it is nudged back on protocol (up to 6 steps).
4. The submitted week is validated; on failure the whole run is retried (up to 3 attempts).
5. The grocery list is built **in code** from the meals' ingredients, merging duplicates and classifying categories. The model never does grocery arithmetic.
6. The week and list are saved, and the email is sent if Resend is configured.

A system-design diagram of the full loop is in [`docs/architecture.md`](docs/architecture.md).

## API

All routes return JSON.

| Route | Method | Purpose |
| --- | --- | --- |
| `/api/week` | GET | Current week, grocery list, and meal logs |
| `/api/generate` | POST | Run the agent, validate, build the grocery list, save, email |
| `/api/meals` | POST | Replace the week's meals (`{ meals }`) |
| `/api/grocery` | POST | Replace the grocery list (`{ grocery }`) |
| `/api/send-list` | POST | Email the current grocery list |
| `/api/log` | POST | Log a meal (`{ mealId, eater, ate, actualDish? }`) or add a preference (`{ eater, newPreferenceText }`) |
| `/api/preferences` | GET | Household preferences and pantry carry-over |
| `/api/household` | GET / POST | Profiles and calorie thresholds (validated; a profile may be incomplete while being set up) |
| `/api/taste/[id]` | GET / POST | A profile's usual meals (`him`, `her` or `toddler`), stored in `data/taste/<id>.md` |
| `/api/suggest-ingredients` | POST | `{ dish }` → ingredient names from the local model, to confirm or edit |

## Data and privacy

- Everything stays on your machine, in `data/`. Runtime files (`current-week.json`, `meal-logs.json`, `household.json`, `data/taste/`) are gitignored, because they hold body measurements and food habits.
- The app talks to your local Ollama, and to Resend only if you set `RESEND_API_KEY`.
- Next.js itself collects anonymous telemetry by default; disable it with `NEXT_TELEMETRY_DISABLED=1`.

**There is no authentication.** The app is designed for a trusted home network or a private overlay network. Do not expose it directly to the public internet.

## Known limitations

- **Model quality matters.** Small local models sometimes return incomplete weeks or ignore constraints. Validation and retries help, but a larger model gives better plans.
- **Hard rules are hard-coded** (for example "no rice at lunch", "no quinoa") in `app/api/generate/route.ts` and `lib/agent.ts`. Edit them for your household; v2 moves them into per-person taste files.
- **Grocery quantities are free text.** There is no unit arithmetic yet.
- **One household, JSON storage.** Fine for a family; not built for many users.
- **No automated tests yet.** `npm test` is a placeholder. Run `npx tsc --noEmit` to type-check.
